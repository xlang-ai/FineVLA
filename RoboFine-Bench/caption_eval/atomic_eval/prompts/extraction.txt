You are an expert extractor for fine-grained robot manipulation descriptions.

Your task is ONLY to extract atomic facts from the provided action description across 10 capability dimensions.

Do NOT do alignment, scoring, or evaluation.
Do NOT rewrite the full text.
Output JSON only.

====================
1. Input Assumption
====================
The upstream pipeline provides:

{
  "sample_id": "...",
  "steps": ["step 1", "step 2", "..."]
}

Important:
- `steps` is a list of ordered manipulation descriptions. It may come from a human annotation (GT) or an AI-generated caption — treat them identically.
- Extract atomic facts from this text only.
- Output JSON only.

====================
2. Capability Dimensions
====================
Use exactly these 10 capability labels and preserve this order in the output:

1. action_sequence
2. active_actor
3. target_object
4. initial_configuration
5. final_configuration
6. contact_and_approach
7. trajectory_and_orientation
8. object_interaction
9. failure_and_recovery
10. body_motion

Capability guidance:
- action_sequence: primitive actions and gripper states.
  Examples: open gripper -> approach mug -> grasp handle -> lift mug -> place on tray -> release; push box forward; grasp bottle -> rotate clockwise -> put it down.
  IMPORTANT: Only extract `gripper_state` when the text **explicitly** mentions "open gripper", "close gripper", or similar. Do NOT infer gripper_state from actions like "grasp" or "release".
- active_actor: which hand/arm acts, ONLY when the text explicitly distinguishes left/right/both.
  Examples: left hand, right hand, both hands, left arm, right arm.
  IMPORTANT: Do NOT extract active_actor for generic single-arm descriptions like "gripper", "finger", "robot arm", or "end-effector". Only extract when left/right/both is explicitly stated.
- target_object: intrinsic attributes of the PRIMARY manipulated object ONLY (the object being grasped, moved, or placed).
  Do NOT extract attributes for supporting objects, reference objects, containers, or placement targets (e.g., "the tray" in "place cup on the tray", "the orange block" in "stack on the orange block").
  Examples: red cup, small metal spoon, white bottle, paper container.
  Do NOT include spatial location here; use initial_configuration for that.
- initial_configuration: the target object's state BEFORE ANY manipulation action begins (the very first state).
  Only extract if the text explicitly describes the starting condition. Do NOT extract intermediate states.
  Examples: bottle upright on the table, plate lying flat in the sink, drawer partially open.
  IMPORTANT: If the text does not describe the object's initial state, return an empty list. Do NOT infer initial state from the action itself.
- final_configuration: the target object's state AFTER ALL manipulation actions are completed (the very last state).
  Only extract if the text explicitly describes the ending condition. Do NOT extract intermediate states.
  Examples: cup on the tray, bottle upright inside the box, drawer fully closed.
  IMPORTANT: If the text does not describe the object's final state, return an empty list. Do NOT infer final state from the action itself.
- contact_and_approach: contact region and approach direction.
  Example: grasp the mug by the handle from above.
- trajectory_and_orientation: movement path or rotation during the action.
  Examples: upward, forward, left, curved, clockwise 90 degrees.
- object_interaction: ONLY secondary/incidental effects on non-target objects that are NOT the primary action itself.
  Example: placing the book shifts the stack; pushing the cup causes the plate behind it to slide.
  IMPORTANT: Do NOT extract object_interaction when the interaction IS the primary action. For example, "insert spoon into cup" is an action_sequence fact (primitive_action=insert) and a final_configuration fact (final_location=in the cup). Do NOT duplicate it as an object_interaction.
- failure_and_recovery: failures, slips, retries, or fail-then-succeed patterns.
  Example: first grasp fails, second attempt succeeds.
- body_motion: base, torso, or camera movement.

====================
3. What Counts as an Atomic Fact
====================
Extract unique, semantically meaningful, independently countable atomic facts.

Represent each atomic fact using:
- `fact_id`
- `step_anchor`
- `object`
- `slot`
- `value`
- `fact_text`

Definitions:
- `fact_id`: unique string within its capability, e.g. `action_sequence_1`, `target_object_2`
- `step_anchor`: a short temporal anchor such as `step_1`, `step_2`, `between_step_2_and_step_3`, or `null` if unclear
- `object`: the target or most relevant object for the fact; use `robot` for base/torso/camera motion; use `null` if unclear
- `slot`: the semantic subfield being described
- `value`: the slot value
- `fact_text`: a self-contained English sentence that fully describes the fact WITHOUT referencing step numbers. The reader should understand the fact from `fact_text` alone, without seeing other facts or knowing which step it belongs to.
  GOOD: "the left arm grasps the purple block from the side"
  BAD: "the left arm acts in step 1"
  BAD: "grasp" (too terse, not a full sentence)

ALL slots by capability (only extract a slot when the text explicitly provides that information; leave slots unextracted if absent):
- action_sequence: `primitive_action`, `gripper_state`
- active_actor: `actor`
- target_object: `category`, `color`, `material`, `shape_or_size`
- initial_configuration: `initial_pose`, `initial_workspace_location`, `initial_relation`, `initial_state`
- final_configuration: `final_pose`, `final_workspace_location`, `final_relation`, `final_state`
- contact_and_approach: `contact_region`, `approach_direction`
- trajectory_and_orientation: `translation_direction`, `translation_extent`, `rotation_direction`, `rotation_angle`, `path_shape`
- object_interaction: `interaction_type`, `affected_object`, `effect`
- failure_and_recovery: `failure`, `retry`, `recovery_result`, `attempt_count`
- body_motion: `base_motion`, `torso_motion`, `camera_motion`

Slot definitions for updated capabilities:

trajectory_and_orientation slots (mutually exclusive — use exactly one slot per fact):
  - `translation_direction`: direction of linear movement (e.g., upward, forward, leftward, toward the right arm)
  - `translation_extent`: distance or magnitude of linear movement (e.g., 10 cm, 0.5 m)
  - `rotation_direction`: rotational direction (e.g., clockwise, counterclockwise)
  - `rotation_angle`: rotation magnitude (e.g., 90 degrees, 180 degrees)
  - `path_shape`: overall shape of the movement path (e.g., straight, curved, arc, L-shaped)

initial_configuration slots (mutually exclusive — use exactly one slot per fact):
  - `initial_pose`: orientation/posture of the object before manipulation (e.g., upright, lying flat, tilted)
  - `initial_workspace_location`: absolute position on the workspace surface (e.g., center of the table, left side of the counter)
  - `initial_relation`: spatial relationship to another object (e.g., next to the cup, inside the drawer)
  - `initial_state`: functional/physical state before manipulation (e.g., lid closed, drawer half-open, held by the left arm)

final_configuration slots (mutually exclusive — use exactly one slot per fact):
  - `final_pose`: orientation/posture of the object after all manipulation (e.g., upright, inverted)
  - `final_workspace_location`: absolute position on the workspace surface (e.g., on the left side of the table, center of the tray)
  - `final_relation`: spatial relationship to another object (e.g., on top of the orange block, to the left of the cabinet door)
  - `final_state`: functional/physical state after all manipulation (e.g., lid open, fully inserted, released)

Examples:
- capability = action_sequence, slot = primitive_action, value = grasp
- capability = action_sequence, slot = gripper_state, value = open
- capability = target_object, slot = color, value = red
- capability = initial_configuration, slot = initial_pose, value = upright
- capability = initial_configuration, slot = initial_workspace_location, value = left side of the table
- capability = initial_configuration, slot = initial_relation, value = next to the cup
- capability = final_configuration, slot = final_workspace_location, value = center of the tray
- capability = final_configuration, slot = final_relation, value = on top of the orange block
- capability = contact_and_approach, slot = contact_region, value = handle
- capability = trajectory_and_orientation, slot = translation_direction, value = upward
- capability = trajectory_and_orientation, slot = translation_extent, value = 10 cm
- capability = trajectory_and_orientation, slot = rotation_direction, value = clockwise

====================
4. Deduplication and Atomicity Rules
====================
Before outputting:
- Split multi-fact phrases into separate atomic facts whenever they express different independently countable facts.
- Keep only semantically meaningful facts.
- Do NOT create facts for pure style words such as "carefully", "smoothly", or "gently".
- Each `fact_text` must be UNIQUE within the same capability.
- If one phrase contains multiple attributes, write separate facts with different `fact_text`.
  Example: use "the cup is white" for color and "the cup is made of paper" for material.
- Do NOT create an extra `action_sequence` fact from a subordinate method phrase.
  Example: if the text says "pick up the cup by lifting it", extract:
  - one `action_sequence` fact for `pick_up`
  - one `trajectory_and_orientation` fact for upward movement
  - NOT a second `action_sequence` fact for `lift`
- Exception: extract `lift` as a separate action only when it is clearly an explicit step in the sequence.

STRICT deduplication — one fact per (capability, slot, object, step_anchor):
- If two candidate facts share the SAME capability + slot + object + step_anchor and their values overlap semantically, keep ONLY the more specific/informative one, discard the other.
  Example (BAD — redundant):
    trajectory_and_orientation, slot=translation_direction, object=block, step=step_2, value="horizontally toward the right arm"
    trajectory_and_orientation, slot=translation_direction, object=block, step=step_2, value="rightward"
  → These describe the same motion phase and same slot. Keep only "horizontally toward the right arm" (more specific).
- Since the updated slots are designed to be mutually exclusive, cross-slot redundancy should be rare. But if two facts across different slots describe the same underlying information, keep only the more informative one.
  Example (GOOD — different slots, genuinely different information):
    final_configuration, slot=final_workspace_location, value="center of the table"
    final_configuration, slot=final_relation, value="on top of the orange block"
    final_configuration, slot=final_pose, value="upright"
  → These are independent attributes. Keep all three.
